# 4. аналитика по реализации н. 2
Если мы хотим делать прямоугольный тайл, то существует всего 2 реализации: тайл для одной из матриц будет квадратным, чтобы гарантировать сохранение прогресса при хождении по результирующей матрице. Если допустим, что его можно не гарантировать, то упремся в то, что чтобы пройти |tile| элементов результирующей матрицы, придется |tile| раз загрузить элементы из матриц, что по сути то же самое, что делать один из тайлов квадратным.

Подбираю оптимальный размер тайла и тред ренжа:
получил закономерность, что в маленьких числах скорость больше. В результате перебора маленьких чисел я засомневался что они все таки хорошие, поэтому вернулся к перебору больших.

Необходимо скипать, если тред сайз больше, потому что иначе нет смысла - бОльшую чем tile size часть мы всегда будем просто отбрасывать. А кратность нужна, чтобы тоже не перебирать лишнего, потому что в противном случае в каждом блоке будет кусочек, который придется игнорировать. Если ренж больше чем 3/4 размера тайла, то тоже мало смысла такое учитывать, потому что потеряем бОльшую часть во второй части.
```c
static _Bool checkTR(size_t ts, size_t tr) {
	if (tr > ts || ts % tr != 0 || tr > ts * 3 / 4) {
		return true;
	}
	return false;
}
```

Зависимость между скоростью и размером локальной группы: 
выявил, что чем меньше элементов в локальной группе, тем дольше работает программа, что крайне логично. То есть например при tile size = 64, thread range = 16, все будет не очень хорошо, ведь элементов в группе будет всего 4. А потенциально там может быть около 16 (в случае квадрата).
**вывод**: надо фильтровать наборы по размеру локальной группы - если маленький, скипаем

##### 2 прохода по thread group или 1
лучше 2, потому что тогда появляется уникальная возможность делать continue и break в случае неудачи, а когда 1 проход, нужно все смиренно проходить чтобы не грохнуть B из-за A или наоборот. Как говорится: "не уходи смиренно в сумрак вечной тьмы".

##### tsw >= tsh
иначе часть потоков в локальной группе, которые должны читать матрицу B простаивают, т.к. потоков выделено ориентируясь под матрицу A, следовательно если в B надо меньше, то часть будет не работать

В твоём случае:

- `TILE_SIZE_K = 66`
- `N_SIZE = 2`
- значит `VECTOR_TILE_SIZE_K = 33`

Почему это плохо? - Это приводит к очень большому локальному tile:
- `aTile` = 16 строк × 33 элементов × 8 байт = 4,2 КБ
- `bTile` = 33 × 2 × 48 × 8 байт = 25,3 КБ
- всего почти 30 КБ LDS на один рабочий блок

На AMD `gfx1010` всего 64 КБ LDS на CU. Значит один блок уже съедает почти половину доступной локальной памяти, и на CU не помещается много одновременно.
